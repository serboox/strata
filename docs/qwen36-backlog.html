3. First target: IQ4_XS above 45 tok/s

IQ4_XS is the first candidate, the lightest file of the Q4 class. Cached, its estimated step is 63 ms (14.9 GPU + 39.8 experts + 8.5 glue), which is 42.7 tok/s at 2.7 tokens per step. Q01 result: the files on Hugging Face lack the MTP block

The header of UD-IQ4_XS (read from the partly downloaded file) and of the current Q4_K_XL on Hugging Face (the first 64 MiB, by range) shows 40 layers and no nextn tensor. Our local Q4_K_XL (21.28 GiB, an earlier upload) has 41 layers: the extra layer blk.40 is the MTP block (20 tensors, 0.49 GiB, nextn_predict_layers = 1). Strata drafts tokens with this block, so a file without it loses the MTP gain: the speeds in section 2 hold only with the block grafted on.

Q09 result: the IQ3_S gate and up rows are the bottleneck, not the read bandwidth

A micro-benchmark on synthetic experts (one expert of 2048 by 512, random weights with valid scales, one thread pinned to a core, the machine not idle, load about 3 to 5) shows how long the CPU spends per expert. UD-IQ4_XS keeps most of its bytes as IQ3_S, and every IQ3_S kernel we had is limited by the number of instructions, not by memory.

With today's kernels one expert of the IQ4_XS file costs 2.5 times the CPU time of one Q4_K_XL expert (about 410 against 165 µs on one thread), although it reads 17 % fewer bytes. With four threads on the busy machine the aggregate was 7.3 thousand experts per second against 15.5 thousand for Q4_K. Put into the step model of section 2 this is an estimate of about 20 tok/s for IQ4_XS, below Q4_K_XL; the 42.7 baseline holds only if the IQ3_S rows become as cheap as the Q4_K rows.

Why: the scalar-lookup kernel runs at 3.7 instructions per cycle (the counters), so it is limited by the instruction count; the gather version needs 2.4 times fewer instructions but takes the same number of cycles. The likely cause is the Downfall microcode mitigation that this CPU reports (gather_data_sampling: Mitigation: Microcode), which makes gather instructions slow.

The new kernel (src/kernels/cpu/iq3s_vbmi.cpp, branch qwen_iq3s_vbmi) replaces the lookups by byte permutes (AVX-512 VBMI) on a grid packed two weights per byte and takes the signs with a bit shuffle (BITALG). Its result matches the ggml dot to a relative 2e-7, which is float rounding. On this CPU a 512-bit vpermi2b costs 3 micro-operations and 2 cycles, so the shuffle port is now the limit; items Q15 and Q16 go further. The numbers were taken with the machine busy: they compare the rows with each other, they are not absolute.

4. What is known about quality

KLD measures how far the quantized model's next-token probabilities drift from BF16. It is not a quality score: a KLD 2.8 times larger (IQ4_XS against Q4_K_XL) does not mean a model 2.8 times worse. The only measured evidence for this model is Unsloth's KLD chart; accuracy on tasks is not published for it.

The nearest published task numbers are for other models. Gemma 3 27B on MMLU (5-shot, BF16 scores 71.5 %):

What is not known: how the loss looks on coding, tool calls and long agent chains. That is what Q04 to Q06 measure; until then the quality columns in section 2 are analogies.

5. Do not break what works

Everything on this page touches the engine that runs today, so the rules of the collection apply in full. The server interface that will choose models (a model reference with a quant, an explain flag, an engine flag) is described in section 1 of the LFM2.5 plan.

Rules that keep what works:
  • Default result unchanged: a start with no arguments gives the same tokens as today, and anything new that is on by default has a flag that switches it off.
  • Every new path sits behind a flag or an engine name that switches it on or off at any time; the owner decides what is on by default.
  • Regression gate: the existing bit-checked checksums of the Q4_K_XL path (MTP 0 and 2, 1.5K and 14K fills) and the llama.cpp parity prompts must come out identical before and after every change; a change that moves them is rejected.
  • Rollback is a flag, not a revert: the engine flag set to legacy, or simply no flag.
  • New work lives in branches and worktrees; main stays untouched until the gates pass.

Capping the CPU frequency: the largest gain so far

Reading memory barely heats the CPU: four threads read 55.6 GB/s for two minutes and the package stayed at 56 to 61 C. The engine reaches 80 C at 37 GB/s, so the heat comes from the arithmetic that unpacks the IQ3_S and IQ4_XS weights, and the heat per token falls faster than the speed when the frequency (and the voltage with it) is lowered.

Capping the highest CPU frequency, with turbo off, more than doubled the sustained speed under the same 80 C limit: 31.1 and 29.8 tok/s in two runs with 6 workers at 2.2 GHz, 28.6 and 27.2 with 4 workers, against 11.0 to 14.8 without a cap (peak temperatures 66 to 80 C in every run). The best setting is the highest frequency at which the governor hardly has to pause the engine: at 2.4 GHz with 6 workers the median falls to 24.9 and the peak reaches 80 C, and at 2.6 GHz with 4 workers it falls to 25.3 with dips to 16.5, because the pauses return. At 2.0 GHz with 6 workers the speed is 28.8 and very even, with a peak of 74 C. The repeats ran through the launcher option, which sets the cap and puts the old limits back by itself. A package power limit (RAPL PL1 at 22 and 18 W, 6 workers, no frequency cap) did not help: 10.2 and 10.4 tok/s, the same as without any limit, because the hardware still runs the CPU at full frequency for bursts and the governor has to pause the engine. The default file, Q4_K_XL, runs at the same setting (2.2 GHz, 6 workers, no pool spin) at 29.4 tok/s with a peak of 74 C, within 5 percent of IQ4_XS, so the choice between the two files is about memory and quality, not speed.

Why the Q4 files differ so much in size and so little in speed

The name does not mean 4 bits. Q4_K_XL stores 60 % of its expert bytes as Q4_K, 37 % as Q5_K and 3 % as Q6_K (4.88 bits per weight on average). IQ4_XS stores 61 % as IQ3_S, 35 % as IQ4_XS and 4 % as Q6_K (3.77 bits). Over the 32 billion expert weights that is the 4.5 to 5 GB between the files. The sizes below are summed from the tensor headers of the files.

Q4_K_XL22.84.880.631.629.4

IQ4_XS17.73.770.471.629.8 and 31.1 (two runs)
IQ3_XXS13.22.760.351.3not measured

Four reasons why the size does not carry over to the speed:

  1. Only 3 % of the experts are read per token. A token needs 8 of 256 experts. A difference of about 5 GB in the file becomes 0.16 GB per token (0.63 against 0.47 GB). Most of the file sits in experts that this token does not touch, so the size decides whether the file fits the memory cache, not how fast a token runs.
  2. The number of calculations is the same. Both files multiply the same 3 billion active weights per token; the quantization changes the bits per weight, not their number. Under the 80 C limit the speed is set by the arithmetic of unpacking the weights, not by reading them (four threads reading 55.6 GB/s kept the package at 56 to 61 C), and unpacking IQ3_S (permutes and signs) is not cheaper than unpacking Q4_K. That is why the IQ kernel gained 14 % in experts per second in the micro-benchmark, not the 25 % that the bytes alone would promise.
  3. About 30 % of a step is the same for every file. By the step model of section 1 (GPU 14.9 ms, experts 52 ms, glue 8.5 ms) the dense part on the GPU, 1.6 GB in Q8_0 in every file, and the glue take 23 ms of 75. Only the experts, about 70 %, can speed up, and by 14 %, so the gain is about 9 %.
  4. The more exact file is guessed better by MTP. The drafts of Q4_K_XL are accepted 69.5 % of the time against 63.5 % for IQ4_XS, which for two drafts (1 + a + a squared) is about 7 % more tokens per step (an estimate, not a separate measurement). That eats most of the remaining 9 %: about +2 % is expected for IQ4_XS, 1 to 6 % was measured.

Where the size does decide (measured). Without the frequency cap IQ4_XS is 14 % faster (14.7 against 12.9 tok/s). With a hard memory budget of 16 GiB it is 20 % faster (16.1 against 13.4), because the file fits the cache and the experts are not read from the SSD. With 12 GiB the order is reversed (13.5 against 15.4), which is not explained yet.

So: choose the file by memory and quality, not by speed: Q4_K_XL when there is memory for about 23 GB of cache, IQ4_XS when a browser and chat programs hold part of it.

How this was computed: the tensor sizes of each GGUF file were summed by group (experts, dense, embedding, head); the bytes read per token are 8/256 of the expert bytes; the sustained speeds are the runs of the frequency section above; the MTP gain uses the accepted share of the drafts in the same runs.

What the numbers say, lever by lever:

  1. Overlap (lever 2): keep, but expect little. All three switches together give +2.8 % on the code prompt and +1.5 % on the text prompt (+1.6 to +2.9 % per step) with a text identical to the baseline's; the self-check (VERIFY_OVERLAP) compared 25216 values with no mismatch, also over a whole 900-token run. Most of it comes from quant (+1.6 %); glue (0.0 %) and commit (+0.4 %) are inside the noise. The timing line of one step (70 ms) reads: GPU wait 14, host glue 2, CPU pool 40, the rest 12; the steps read 594 to 801 weight sets for 976 to 992 entries, so the rows share 20 to 40 % of the reads, which a row pipeline (Q33) would give up while it could hide at most the 14 ms of GPU wait. It was not built, and the numbers say it should not be.
  2. Experts on the iGPU (lever 3): do not use. Every variant loses: -48 % with one entry per layer, -60 % with two, -66 % with four, -64 % with eight (share 0.25), -61 % (share 0.35), -63 % (share 0.15). A step takes 150 to 223 ms instead of 73 ms: one iGPU call takes about 2 ms even for one entry, as long as the whole CPU pool needs for a layer, so the pool waits for the iGPU in every layer (the statistics line shows a join wait of 40 to 190 ms per step). The code stays in the tree, off by default and out of the default build.
  3. Fewer experts (lever 4): the one lever with a large gain, and it costs quality. The tokens per second also move with the share of MTP drafts that are accepted, which depends on the text, so the time of one step is the fair measure: 7 of 8 experts +10.8 % per step on the code prompt and +8.6 % on the text prompt (tokens per second +17.2 % and +6.4 %, because the drafts were accepted 71 % against 64 % on the code and 60 % against 62 % on the text); 6 of 8 +19.0 % and +18.9 % per step (+20.9 % and +20.0 % in tokens per second); 5 of 8 +32.1 % per step (+35.3 %). Against the same file at 8 experts (16 thousand tokens of documents and code) the mean KL divergence is 0.025, 0.060 and 0.122, the best token is the same in 93.1 %, 89.3 % and 85.3 % of positions, and the perplexity rises by 1.7 %, 5.4 % and 10.8 %. For scale: the whole step from Q4_K_XL to IQ4_XS costs about 0.01 of KLD. 7 experts is the only count that looks acceptable without a test on real tasks; 6 and 5 change the answers noticeably. Quality on tasks (tool calls, agent) is not measured.
  4. Dense part in Q6_K (lever 5): drop. The three groups attention, GDN and shared expert: +1.1 % (+0.9 % per step), inside the noise, against the expected 3 to 4 %: the Q8_0-only fast paths are lost. All groups, with the embeddings and the MTP projection: +9.7 % on the code prompt but only +3.2 % per step (the drafts were accepted 72 % against 64 %), and +2.9 % on the text prompt (+0.5 % per step). The quality cost is real: KLD 0.0124 and 0.0125 against the plain file, best token the same in 95.1 %.

Combinations. Overlap with 7 experts: +17.1 % (7 experts alone: +17.2 %); overlap with 6 experts: +23.1 % (6 alone: +20.9 %). The overlap adds about as much on top as it gives alone, one to two points, which is at the edge of the noise. Adding the dense Q6_K does not help: overlap + Q6_K +3.8 %, 7 experts + Q6_K +15.3 %, all three together +15.2 %, all below overlap with 7 experts. The iGPU was left out of the combinations because it loses by itself. The text differs from the baseline in every run that has fewer experts or the Q6_K file, as it must; the baseline's own repeat is identical.

The best setting found. Overlap with 7 experts per token: 36.0 tok/s against 30.8 on the code prompt (+17 %, of which about +12 % per step and the rest a higher share of accepted drafts), package at most 67 C, at the price of a KL divergence of 0.025 (top-1 the same in 93 %). The only change that costs nothing in quality is the overlap, and it gives about 2 to 3 % per step. The price of the larger gains is quality, which the tasks of C03 to C06 would have to confirm.

Cooling (lever 1). The kit on the balanced profile (caps 2.2, 2.4, 2.6 GHz, 300 s of continuous load per step): sustained 30.3, 26.6 and 21.7 tok/s; the package reached 80 C after 468 s at 2.2 GHz and after 177 s at 2.4 GHz, with the hottest sample at 82 and 83 C; at 2.8 GHz it reached 80 C within 6 seconds, while the model was still loading, so no speed could be measured. So 2.2 GHz stays the best cap, and a long continuous run at 2.2 GHz still touches the limit; the short lever runs stayed at 70 C. The platform profile matters: the low-power profile (set without root) keeps the package at 63 to 65 C but costs a third of the speed (20.7 and 20.8 tok/s at 2.2 and 2.4 GHz), and the cap stops mattering. The profile above balanced could not be tested: the firmware refuses performance (reported as degraded for the operating temperature), balanced-performance needs a root write, and that test was declined, so it was not run. The fan sensors read 0 throughout and are marked unreliable.

Without the IQ kernels (series 1). The same plan with the AVX-512 kernels for the IQ experts off, which is how the engine runs a build without them: the baseline is 17.3 tok/s (138 ms per step instead of 74). The overlap gives nothing here (+0.6 % per step), 7 experts +8.7 % per step, 6 experts +21.5 %, 5 experts +36.7 %, and the experts on the iGPU lose 32 to 37 % (less than with the kernels, because the CPU is slower). So the gains from fewer experts do not depend on the kernels, and the overlap only shows when the CPU part is fast.

7. Execution

Order that wastes the least: Q01 and Q02 first (cheap, they decide whether the rest is possible), then Q03 for IQ4_XS and the step profile Q08; the levers Q09 to Q12 and the quality gate Q04 to Q06 follow, and Q07 chooses the quant.

Rules for every run

  • Before each phase read ~/.claude/usage.json; at 99 % or more, wait for the reset instead of pushing on.
  • Measure only on a quiet machine: record the load average and discard a run if other load exceeds 1.
  • Development tests are light: at most two threads, niced, synthetic experts, a few seconds per point. The whole machine is used only for Q20, after the owner has freed it and said so.
  • Servers run in the background scope; builds use at most 6 of 8 threads, runs 4 threads, always niced.
  • Every item has a 90 minute box, every question 15 minutes of reproduction, every loop a counter and a timeout. At the box, report what exists.
  • Results go to docs_private/experiments/qwen36/*.json.
  • One logical change per commit, after the local checks and the Codex review; no push to main without an explicit go.
  • After each phase: a Telegram milestone note, then a cleanup sweep: processes, temp files, downloaded models that are no longer needed, and a check that disk space came back.
