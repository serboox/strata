1. Direction: a collection of engines, not one engine for one card

Today the repository holds engines for the RTX 3050 Ti Laptop only. Other cards are expected later, so the rule is: nothing may bake the 4 GiB laptop in. The LFM2.5 work is the first test of that rule: it pushes the model-specific parts (about 5.4k of 31k lines) behind an interface, and it turns the hard-coded 4 GB split into a plan computed from a measured hardware profile. Engines for other cards are not built now; the interfaces only have to leave room for them.

Support matrix: model × hardware

Scope (decided): the repository includes engines for the RTX 3050 Ti Laptop only. The cards that docs/index.html names as reference points (RTX 3090, 3090 Ti, 4090, 5090, 5070, 3060, Radeon AI PRO R9700) are not targets today. The one rule that keeps the door open: every card-specific number comes from a profile file, never from code, and nothing is built for a card that does not exist yet beyond an interface and a stub.

Three regimes, three engine flavours

Resident share comes from the model in section 3 (Q4_K_XL, 32K context, f16 KV, 0.6 GiB runtime buffers assumed). Only the offload flavour is built now; the other two are described so that the interfaces leave room for them.

How the server will choose, and how switching stays safe

The idea is a Strata server that takes a model reference and works out the rest. Proposed interface (only the no-argument start exists today):

strata-serve                                              as today: Qwen3.6 Q4_K_XL, same flags, same output
strata-serve --model qwen3.6-35b-a3b@iq4_xs               a model reference: family, size and quant
strata-serve --model lfm2.5-24b-a2b@q4_k_xl --gpu auto
strata-serve --model qwen3.6-35b-a3b@iq4_xs --explain     print the plan, start nothing
strata-serve --engine legacy                              force the current code path at any time
InputHow it is resolved
Model reference (family, size, quant)a manifest: file, tokenizer, chat template, tool-call dialect, state layout
GPUdetected by the probe; the flag overrides it with a profile file
RAM budgetthe existing budget and profile flags, unchanged
Planplacement of weights, chunk size, MTP draft count; shown by the explain flag
Enginechosen by the plan; the engine flag forces the current path
  • The GPU is not a required input: it is detected, and the flag only overrides it. A name alone says little; the numbers that matter (VRAM, bandwidth, PCIe) come from a measured profile.
  • The quant belongs in the model reference: on this laptop it moves the speed more than the choice of model does (section 3).
  • The explain flag prints the plan with its reasons (what lives in VRAM, what in RAM, what is read from disk), so a surprising speed has a visible cause.
  • Switching is a restart with another flag, a matter of seconds. A live swap without a restart is not planned: 31 GB of RAM cannot hold two models, so a swap would unload the first one anyway.
  • A model whose tensor types the engine cannot read is refused up front with a clear message (item Q01 of the Qwen3.6 plan), not in the middle of loading.
Rules that keep what works:
  • Default result unchanged: a start with no arguments gives the same tokens as today, and anything new that is on by default has a flag that switches it off.
  • Every new path sits behind a flag or an engine name that switches it on or off at any time; the owner decides what is on by default.
  • Regression gate: the existing bit-checked checksums of the Q4_K_XL path (MTP 0 and 2, 1.5K and 14K fills) and the llama.cpp parity prompts must come out identical before and after every change; a change that moves them is rejected.
  • Rollback is a flag, not a revert: the engine flag set to legacy, or simply no flag.
  • New work lives in branches and worktrees; main stays untouched until the gates pass.

3. Performance model (estimates, with the formulas in the open)

Tokens per second: how it was and what to expect

Measured rows come from docs/TUNING.md (the same machine, greedy decoding of one code prompt, cool CPU). Estimate rows are computed from the measured bandwidth and the bytes read per token; each one is replaced by a measurement in P1. Only the offload regime of this 4 GiB card is covered.

measured (Qwen3.6)estimate (LFM2.5): dark bar up to the cautious value, light bar up to the optimistic one
Estimate rows: a single-token step is GPU 6 ms (0.85 GB of non-expert weights at 172 GB/s, plus launch overhead) + experts on the CPU (876 MB at the 29 GB/s the engine achieves; the machine's ceiling is 54 GB/s) + 5 ms of glue, about 41 ms or 24 tok/s. The same method gives about 37 ms for one Qwen token, which matches the measured 36.5 ms (llama.cpp) and 37.7 ms (Strata without MTP, long context), so the method is calibrated on a measurement. Each lever scales the CPU part: 15 % of the experts in VRAM leaves 85 % of the bytes; the IQ3-class mix reads 58 % of them. Under sustained heat expect about 25 % less (measured on Qwen: 35.6 down to 25.9 tok/s). The 16G budget hurts Qwen (21.1 to 25.4) because its 22 GB file does not fit; the 14 GB file of LFM does, so no drop is expected there.
Prompt reading is limited by streaming the experts over PCIe in every pass: Qwen streams about 18.7 GB per pass of 512 tokens (6.1 GB/s × 3.07 s, from TUNING.md), LFM about 11.9 GB (14.0 GB of experts minus roughly 2 GiB kept in VRAM), so the ceiling rises by about 1.57×. The estimates take 1.3 to 1.57× of the Qwen numbers; for llama.cpp a larger share of a 14 GB file fits in the 9G page cache. With the CPU computing part of the experts and the model fully cached, Qwen reaches 183 to 205 tok/s on a 1546-token prompt; the same scaling would give about 240 to 300 for LFM.
Bottom line (estimates): with no change of the weights LFM2.5 is expected at 28 to 32 tok/s after D01 and D02, about what Qwen with MTP gives today (33.1). Only the IQ3-class mix (class L1, needs the quality gate) lifts it clearly higher, to 33 to 42. Prompt reading is where LFM2.5 should win, by 30 to 55 %.

LFM rows are estimates: GPU 6 ms, experts 876 MB at the 29 GB/s the engine achieves (the ceiling is 54 GB/s, which would give 16 ms), glue 5 ms. The IQ3 row assumes the experts shrink with the file (7.55 vs 13.06 GiB) and that CPU dequantization keeps up, which is not certain. P1 replaces every assumption here with a measurement.

Reading: LFM is not faster per token on this card. Its experts are large (top 4 of 64, each 1536 wide), so a token reads 876 MB of them against about 510 MB for Qwen, and speculation does not rescue it: checking 3 tokens reads about 2.9 times the expert bytes (a step of about 102 ms), a gain of only about 1.08× at 2.7 tokens per step. The speed has to come from fewer bytes (IQ3-class experts, D09), more experts in VRAM (D01, D02), and from prompt reading and cache reuse (D03, D04), because agent sessions spend most of their time reading prompts, not decoding.

5. "No quality loss" as a contract

Every lever is placed in one of three classes, and a lever may be merged only when it passes the gate of its class. Numeric thresholds are fixed by C11 from the measured noise floor (Q8_0 against itself, different batch sizes), not guessed now.

ClassMeaningGateExamples
L0 losslessSame math, same tokensGreedy output identical to the reference on the whole prompt set; identical logits within the noise floorplacement, expert residency, chunk size, prefix cache, n-gram speculation
L1 near-losslessWeights or cache are rounded differentlyKL divergence and top-1 agreement within a set multiple of the noise floor, and no regression on tool-call and long-context testsKV q8_0, expert quant mix, own-trace imatrix, dropping old thinking from history
L2 behavioralChanges what the model is allowed to doPaired agent tasks (C05, C06) non-inferior, with the sample size stated and "directional" written when it is too smallthinking budget cap
Two traps to keep in mind: a lever that edits the prompt history (D11) changes the cached prefix, so it must be applied consistently or every turn misses the cache; and speculation on a MoE model verifies k tokens by reading up to 4k experts per layer, which can eat the bandwidth it was meant to save (D06 measures the accepted length and the real step cost).

8. Execution plan

Effort by phase (class midpoints)

S 0.5 h, M 2 h, L 5 h, XL 16 h of wall-clock including waiting for builds and runs. A planning figure, not a promise. Most H items run unattended.

Rules for every run

  • Before each phase read ~/.claude/usage.json; at 99 % or more, wait for the reset instead of pushing on.
  • Measure only on a quiet machine: record the load average and discard a run if other load exceeds 1.
  • Servers run in the background scope; builds use at most 6 of 8 threads, runs 4 threads, always niced.
  • Every item has a 90 minute box, every question 15 minutes of reproduction, every loop a counter and a timeout. At the box, report what exists.
  • Results go to docs_private/experiments/lfm25/*.json; this page is regenerated from them (G01).
  • One logical change per commit, after the local checks and the Codex review; no push to main without an explicit go.
  • After each phase: a Telegram milestone note, then a cleanup sweep: processes, temp files, build directories, downloaded models that are no longer needed, and a check that disk space came back.
Order that wastes the least: A02 to A04 and F11 first (cheap, unblock everything), then B01 and B07 (the two numbers every decision needs), in parallel with the platform lane (F03 and F04 do not depend on LFM results). The Qwen3.6 plan (a separate page, qwen36-backlog.html) runs in parallel too, starting with IQ4_XS and aiming above 45 tok/s: it is the cheaper route to a faster model and sets the bar that LFM has to beat. The decision gate E01 comes only after B07, C05, C06, D04 and D09.
