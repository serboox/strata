Что именно хранится в VRAM

Strata, Qwen3.6-35B-A3B (UD-IQ4_XS с блоком MTP), видеокарта RTX 3050 Ti Laptop на 4 ГБ. Состояние на 3 ноября 2026, конфигурация по умолчанию: контекст 65536 ячеек, блок промпта 512, KV-кэш в q8, одна сессия, MTP 2 черновика.

Коротко. В VRAM лежит только «плотная» часть модели, которую считает видеокарта на каждом токене (внимание, рекуррентные слои GDN, общий эксперт, роутеры, голова вывода): 1.92 ГиБ. Рядом лежат кэш внимания (748 МиБ при контексте 65536), состояние GDN (63 МиБ), рабочие буферы и контекст CUDA. Всего процесс движка занимает 3496 МиБ, свободно остаётся около 0.27 ГиБ. Маршрутизируемые эксперты (14.6 ГиБ) и таблица эмбеддингов (0.5 ГиБ) в VRAM не лежат: эксперты читает из оперативной памяти CPU, таблица эмбеддингов закреплена в RAM, и видеокарта берёт из неё нужные строки по PCIe.

Оговорка о числах. Каждое число ниже помечено, откуда оно взято: измерено (лог движка, nvidia-smi, заголовок файла GGUF), посчитано (по формулам из кода движка и геометрии модели), оценка (остаток, который я не смогла разложить по статьям без запуска движка под отладчиком).

1. Общая картина

Что сказали измерения. Во время прогона nvidia-smi показывал для процесса движка 3496 МиБ (вся карта 3527 МиБ, остальное приходится на рабочий стол). Лог движка при старте: «1.92 GiB on the GPU», «scratch buffers 80 MiB», «context 65536 cells ... 0.27 GiB of VRAM free». Значит CUDA видит около 3773 МиБ (3496 + 277), то есть около 323 МиБ из 4096 номинальных занимает драйвер и прошивка.

Почему здесь Q8_0, а не Q4?

Названия «UD-IQ4_XS» и «UD-Q4_K_XL» описывают рецепт квантования Unsloth Dynamic, а не один тип на весь файл: слои подбираются по чувствительности. Основная масса байтов действительно хранится в 3-5-битных типах, а небольшие плотные тензоры, через которые проходит каждый токен, Unsloth держит в Q8_0. Итог: у обоих файлов около 86-88 % байтов приходится на эксперты в «четвёрочных» типах, и около 11 % на Q8_0 (1978 МиБ у IQ4_XS, 2494 МиБ у Q4_K_XL). Q8_0 вы видите потому, что смотрите на то, что лежит на GPU: именно этот слой модели Unsloth оставляет почти без потерь, чтобы не портить каждый токен. Эксперты, которых за токен активно только 8 из 256, квантуются агрессивно. Это обычный подход Unsloth Dynamic; точный перечень слоёв, которым оставили высокую точность, определяется их калибровкой и в нашем коде не настраивается.

3. Что в VRAM не лежит

Маршрутизируемые эксперты: 14.1 ГиБ + 0.45 ГиБ у MTP

256 экспертов на слой × 40 слоёв, на токен активны 8. Движок читает их «на месте» из отображённого файла GGUF (кэш страниц RAM), считает их пул из 4 потоков CPU, а результат отправляет на GPU. В логе: «hybrid experts: 0 of 256 per layer in VRAM, all 14.66 GiB read in place from the mapped GGUF». Один эксперт IQ4_XS занимает 1.39 МиБ (gate+up 0.86 МиБ, down 0.53 МиБ); свободных 277 МиБ хватило бы на 198 экспертов из 10240, это 1.9 %. По замерам из docs/TUNING.md 75 экспертов покрывают всего 0.8 % обращений, поэтому кэш горячих экспертов в VRAM почти ничего не даёт.

Таблица эмбеддингов: 0.5 ГиБ

По умолчанию лежит в закреплённой памяти RAM, и GPU читает нужные строки напрямую по PCIe (комментарий в коде: «Host (the default): in pinned host memory the GPU reads through PCIe»). На токен нужна одна строка в 2 КиБ, поэтому это почти ничего не стоит, а в VRAM экономит 0.5 ГиБ.

Контрольные точки префикса, tokenizer, сам файл

Контрольные точки (--ckpt 6), очереди запросов, токенайзер и GGUF живут в RAM и на диске, не в VRAM.

4. Состояние сессии

4.1. KV-кэш внимания: 748 МиБ при контексте 65536 посчитано

Полное внимание только в 10 слоях из 40, плюс один слой блока MTP: 11 слоёв с кэшем. У модели 2 KV-головы по 256 значений. В режиме --kv q8 строка головы хранится блоками по 32 значения (2 байта масштаб + 32 байта значений = 34 байта), то есть 8 блоков = 272 байта на голову. Ячейка K и V вместе: 2 головы × 272 × 2 (K и V) = 1088 байт на слой, 11 слоёв: 11 968 байт на ячейку. Это число совпадает с «+11 968 байт на ячейку» в docs/TUNING.md.

При контексте 65536: 11 968 × 65 536 = 784 334 848 байт = 748 МиБ. В режиме f16 было бы 2 × 512 байт на голову, 22 528 байт на ячейку и 1408 МиБ, поэтому по умолчанию используется q8.

4.2. Состояние GDN: 63 МиБ на сессию посчитано

У каждого из 30 слоёв GDN есть фиксированное рекуррентное состояние, не зависящее от длины контекста: матрица S размером 32 головы × 128 × 128 в F32 (2 МиБ) и состояние свёртки 8192 канала × 3 в F32 (96 КиБ). Итого 2 195 456 байт на слой, 65 863 680 байт или 62.8 МиБ на сессию. Если у сервера несколько параллельных сессий (--batch), каждая получает свой комплект K/V и GDN.

Это контекст CUDA процесса (драйвер, таблицы страниц; типично 200-300 МиБ на такой карте), рабочие области cuBLAS и cuBLASLt, рабочая область GEMM для промпта, буферы MMQ и нативных ядер экспертов, и загруженные модули ядер. Ядра грузятся лениво (CUDA_MODULE_LOADING=LAZY): без этого сотни мегабайт ушли бы на модули ядер сразу при старте, а на 4 ГБ каждая сотня мегабайт на счету. Разложить остаток по статьям можно, только запустив движок с трассировкой cudaMalloc; я этого сейчас не делала, потому что Вы просили отложить всё, что связано с запусками.

Чего в VRAM нет, хотя могли бы подумать. Копий Q8_0-весов в «упакованном» виде для быстрых ядер: они отключены (STRATA_Q8_PACKED=0), иначе плотные веса занимали бы вдвое больше. Экспертов-слотов: 0 из 256 на слой (при --expert-slots N каждый слот стоит 1.39 МиБ на слой, то есть 56 МиБ на слот сразу для 40 слоёв). Буфера подкачки экспертов для длинных промптов: в логе «0.00 GiB staging».

6. Как это меняется

Калькулятор: свободная VRAM при других настройках. Это оценка по формуле, откалиброванной на одном замере (3496 МиБ при контексте 65536, q8, одна сессия, блок 512, --att-scores 4); для другого блока промпта или другого файла она сдвинется.

K/V-кэш всех сессий: 748 МиБ

Состояние GDN всех сессий: 63 МиБ

Занято процессом: 3496 МиБ из 3773

Свободно: 277 МиБ

Столько экспертов IQ4_XS влезло бы в слоты: 198 (из 10240)

  • Контекст. Каждые 8192 ячейки стоят 93.5 МиБ в q8. Контекст 16K освободил бы около 0.55 ГиБ, то есть примерно 400 экспертов (3.9 %): слишком мало, чтобы окупить потерю длинного окна.
  • Блок промпта (--chunk) и --att-scores. Растут буферы: около 0.5 МиБ на токен блока и 12 МиБ на каждые 4 Mi значений оценок. По таблице в docs/TUNING.md блок 1024 уже не помещается рядом с контекстом 32768 на Q4_K_XL.
  • Голова вывода. Q6_K у IQ4_XS экономит 117 МиБ против Q8_0 у Q4_K_XL: по этой причине у IQ4_XS остаётся 0.27 ГиБ свободных вместо примерно 0.14 ГиБ.
  • Слоты экспертов в VRAM (--expert-slots): каждый слот на 40 слоёв стоит 56 МиБ. На 277 МиБ влезло бы около 4 слотов на слой, то есть 1.6 % экспертов.
  • Слоты в закреплённой памяти RAM (новая опция --host-slots в ветке qwen_host_slots, ещё не проверена замером): слоты лежат в RAM, а GPU читает их по PCIe напрямую (проверено: 6.0 ГБ/с, pageableMemoryAccess работает). VRAM они не занимают.

7. Как проверить самому

# сколько занимает процесс движка (во время работы сервера)
nvidia-smi --query-compute-apps=pid,used_memory --format=csv

# разбивка типов тензоров любого GGUF по группам
python3 -c "
import sys, collections
sys.path.insert(0, 'tools'); import gguf_reader
g = gguf_reader.GGUFFile('models/qwen3.6-35b-a3b/Qwen3.6-35B-A3B-UD-IQ4_XS-mtp.gguf')
print(g.by_type())"

# строки лога движка со стартовым учётом VRAM
grep -E 'on the GPU|scratch buffers|context .* cells|hybrid experts' logs/strata-qwen36.log
